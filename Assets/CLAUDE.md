## Architecture

There are **two decoupled halves**: a **physics simulation** and a **URP rendering pipeline**, meeting at a data hand-off. In Unity 6 the renderer reads particle state out of the pure-data sim; **in this repo today the renderer still reads GameObject Transforms** — closing that gap is the whole point of the port.

### Current state — what actually exists in this repo

**Particle model — GameObject-based (original pre-SPH design).** Each particle is an instance of `Assets/Prefabs/Liquid2DParticle.prefab`, which carries exactly four components: `Transform`, `Liquid2DParticleRenderer` (MonoBehaviour), `CircleCollider2D` (radius 0.5, physics material), `Rigidbody2D` (dynamic, gravity). There is **no SpriteRenderer** — particles are drawn only by the custom render feature. "Fluid" is purely a *rendering* trick (draw circles → blur → alpha-cutoff = metaballs); motion is Unity's built-in `Rigidbody2D` physics, **not a fluid solver**.

- **`Source/Liquid2DParticleRenderer.cs`** (`[ExecuteAlways]`) — registers/unregisters the particle into a static dictionary on `Liquid2DFeature` (`OnEnable`/`OnDisable`), grouped by `Liquid2dParticleRendererSettings` (keyed on sprite+material). Only carries render settings + exposes its `Transform`.
- **`Source/Liquid2dParticleRendererSettings.cs`** — plain `[Serializable]` class (sprite / material / HDR color / `liquid2DLayerMask`). Note the **`public` serialized fields** here diverge from the coding conventions below (legacy; see conventions section).
- **`Physics/pm_water.physicsMaterial2D`** (friction 0, bounciness 0.01) and **`pm_magma.physicsMaterial2D`** (friction 0.8, bounciness 0.1) — the only "physics config" today.

**Rendering — URP 14 ScriptableRenderPass (Compatibility Mode, no Render Graph).** `Source/Liquid2DFeature.cs` is a `ScriptableRendererFeature` whose nested `Liquid2dPass : ScriptableRenderPass` runs at `RenderPassEvent.BeforeRenderingPostProcessing`. Per frame (`Execute(ScriptableRenderContext, ref RenderingData)` with a pooled `CommandBuffer`):

1. **Draw particles** into an HDR (`ARGBHalf`) `_liquidDrawRT`: iterate the registered-particle dictionary, filter by layer mask `(item mask & feature mask) == 0`, build a `Matrix4x4.TRS` **from each particle's live Transform**, batch via `cmd.DrawMeshInstanced` (GPU Instancing, per-instance `_Color`) using `Source/Shaders/Liquid2DParticle.shader`.
2. **Blur** (`Source/Shaders/Liquid2DBlur.shader`, Kawase): copy to quarter-res blur RTs, iterate `iterations` times, offset `0.5 + i*blurSpread`.
3. **Composite** (`Source/Shaders/Liquid2DEffect.shader`) onto the camera color: `clip(a - _Cutoff)` metaball silhouette + alpha offset. (Edge/saturation blocks exist but are commented out.)

RT management uses URP 14 `RTHandle` + `RenderingUtils.ReAllocateIfNeeded`; camera color via `renderingData.cameraData.renderer.cameraColorTargetHandle`. Both feature instances live on `Settings/Renderer2D.asset` ("Water": mask 2, iterations 7, blur 0.6; "Magma": mask 4, iterations 4, blur 0.4).

**Layer-mask system (`Source/ELiquid2DLayer.cs`).** A `[Flags]` enum (`Default=1`, `Water=2`, `Magma=4`, `Marsh=8`). It links **particle ↔ feature ↔ volume**: a particle is drawn by a feature only if their masks overlap. This is the 2022 analogue of Unity 6's `nameTag` + Rendering-Layer-Mask coupling — **but note it is a fixed flags enum, not string tags or URP rendering layers.** Multiple features coexist, each rendering one layer with its own blur config.

**Volume overrides (`Source/Volumes/`).** `Liquid2DVolume : VolumeComponent` holds a `List<Liquid2DVolumeData>` (each keyed by `nameTag`). `Liquid2DFeature.UpdateSettings()` merges the matching volume entry over the default feature settings each `Execute` (overriding `iterations` / `blurSpread` / `liquid2DLayerMask`). `StringParameter.cs` / `UIntParameter.cs` are declared but unused (leftovers). Editor: `Editor/Volumes/Liquid2DVolumeEditor.cs` currently just calls `base.OnInspectorGUI()` (custom mask UI is commented out).

### Target state — being ported from Unity 6 (algorithm authority = the Unity 6 repo)

- **Physics — pure-data SPH.** No per-particle GameObjects; particles become rows in Structure-of-Arrays `NativeArray` buffers advanced by an SPH **dual-density** solver (`Liquid2DSimulation` hub driven in `FixedUpdate`, `Liquid2DParticleStore` SoA store, `ILiquid2DSolver` with CPU Job+Burst and GPU compute paths, `Liquid2DParticleDescriptor` ScriptableObject replacing the prefab, scene-authored collider / force-field / dead-zone MonoBehaviours flattened to Burst buffers each frame, `Liquid2DRigidbodyBridge` two-way coupling). **【留白 / TODO：移植范围——CPU 路径优先 / 是否同时移 GPU compute 路径 / 是否保留 GameObject 兼容层——待确认。】**
- **Renderer — rework to read the sim, not Transforms.** The renderer must consume the sim's data hand-off (`Liquid2DSimulation.TryGetRenderData` for CPU SoA + active indices; `TryGetRenderBuffers` for GPU-resident `ComputeBuffer`s via `DrawProcedural`; `GetRenderableAliveCount` for the per-feature early-out) instead of iterating registered Transforms. ### The key architectural shift

The port moves particles from **"one GameObject + Transform + Rigidbody2D each"** to **"pure data (SoA slots) advanced by an SPH solver"**. This changes three things at once: how particles *exist*, the spawn/despawn API (Unity 6: `Liquid2DSimulation.Instance.Spawn/Despawn` returning `Liquid2DParticleHandle`), and how the renderer *reads positions* (sim buffers, not Transforms). Physics is **play-mode only** in the Unity 6 model (sim runs on `FixedUpdate`, `Instance` is null in edit mode).

## Physics port notes

The physics/solver layer is **"almost fully reusable"** — verified against the Unity 6 sources:

- **CPU solver is copy-paste-grade portable.** `ILiquid2DSolver`, `SolverParams`, `Liquid2DHashGrid`, `SphCpuSolver`, `SphJobs`, `Liquid2DParticleStore` use only classic `NativeArray` / `NativeList<int>`, a **hand-rolled counting-sort hash grid** (over plain `NativeArray<int>`), and stock `IJob` / `IJobParallelFor` + `[BurstCompile]`. **No `NativeParallelHashMap` / `NativeHashMap` / `NativeMultiHashMap`** — so the well-known Collections 1.x↔2.x rename footgun **does not apply**. No `Awaitable`, no Entities/DOTS, no `GraphicsBuffer`.
- **Required packages — must be added to `Packages/manifest.json` AND resolved in the editor** (none are currently present; in Unity 6 they resolve transitively). **Claude can edit `manifest.json`, but package download/import/recompile must happen inside the Unity Editor — a manual step for the user.**

  - `com.unity.collections` — **must be the 1.x line (e.g. `1.5.1`); do NOT install 2.x** (2.x targets Unity 6/2023+).
  - `com.unity.mathematics` — **【建议 `1.2.6` 或 `1.3.2`，待确认】**
  - **Do NOT add `com.unity.jobs`** — the `IJob`/`JobHandle` types resolve via `com.unity.collections` + the engine module; the standalone `com.unity.jobs` 0.x is deprecated and will cause type conflicts.

## Rendering port notes

- **This is the largest port cost.** Unity 6's `Liquid2DPass.cs` is **entirely Render Graph** (`RecordRenderGraph`, `AddRasterRenderPass<PassData>`, `TextureHandle`/`TextureDesc`, `builder.SetRenderAttachment`/`UseTexture`, `RendererListHandle`, `AddBlitPass`, `frameData.Get<Universal*Data>`, `resourceData.activeColorTexture`). **None of this exists in URP 14.0.12.** It must be rewritten imperatively as `ScriptableRenderPass.Execute(context, ref renderingData)` + `CommandBuffer` + `RTHandle`/temp RTs + `Blit`/`Blitter` + `CoreUtils.SetRenderTarget` (incl. the two-target MRT in GrabAsBg) + `context.DrawRenderers`. **The existing `Source/Liquid2DFeature.cs` already uses exactly this URP 14 pattern and is the right skeleton to grow.**
- **What ports (nearly) verbatim:** the 8 shaders (`GetFullScreenTriangleVertexPosition` / `TEXTURE2D_X` / StructuredBuffers are pipeline-agnostic), the draw-call bodies (`DrawMeshInstanced`, `DrawProcedural` with `ComputeBuffer`, `MaterialPropertyBlock`), the sim→renderer hand-off contract, the nameTag gate, and the Volume `CopyFrom` merge pattern. `DrawProcedural`/`ComputeBuffer`/`GraphicsBuffer`/`MaterialPropertyBlock` all behave identically on 2022.3.

## Conventions / gotchas

- **Two rendering "eras" coexist in the docs:** anything called "Render Graph / `RecordRenderGraph` / `TextureHandle`" belongs to Unity 6 and is **not** valid here. This repo is URP 14 Compatibility Mode (`Execute` + `CommandBuffer` + `RTHandle`).
- **`ELiquid2DLayer` (flags enum) ≠ Unity 6's `nameTag` (string) / URP Rendering Layers.** When porting Unity 6 code that keys on `nameTag`, decide how it maps onto this repo's layer model (**【留白 / TODO】**). An empty/`Default` selection semantic must be preserved: a particle should still be drawable by a matching feature.
- **Trilingual docs (Unity 6 convention, keep when adding new package code):** public API XML comments in Chinese / English / Japanese; inspector tooltips via a `LocalizationTooltipAttribute(zh, en, ja)`. **Note this attribute does not exist in this repo yet** — it lives in the Unity 6 package (`Runtime/Source/Localization/`); port it if/when needed. `[Header(...)]` uses English only.
- **`.meta` files**: never hand-create; let the editor generate them.
- Editor-only code is guarded by `#if UNITY_EDITOR` (or lives under `Assets/Editor/`).
- **Burst/native cleanup** (once the physics is ported): every `NativeArray` / `NativeList` / `ComputeBuffer` must be disposed; TempJob buffers freed each frame. Mirror the Unity 6 `try/finally` around `_solver.Step` and `OnDestroy`.
- Shaders are resolved by `Shader.Find("Custom/URP/2D/...")` (Unity 6) or by serialized `Shader` references on the feature (this repo).

## Unity coding conventions

- **Inspector fields stay private.** Any field that is serialized and exposed for editing in the Inspector is always declared `private` with `[SerializeField]` — never `public`. This applies to every serializable context: `MonoBehaviour`, `ScriptableObject`, and plain `[Serializable]` data classes/structs nested in them. When such a field must be read or written from outside the class, expose a dedicated accessor property instead of widening the field's visibility.
  - ⚠️ **Existing divergence:** `Liquid2dParticleRendererSettings`, `Liquid2DFeatureSettings`, and `Liquid2DVolumeData` currently use `public` serialized fields. This is legacy from the initial 2022 framework. Prefer the private+`[SerializeField]` form for **new** code; only refactor the existing ones deliberately (renaming a serialized field breaks saved YAML — see below).
- **Public field naming: PascalCase.** Public fields (e.g., in `[Serializable]` data classes) use PascalCase (`Position`, `Size`, `DebugColor`). Private fields use `_camelCase` with a leading underscore.

### C# identifier naming

Follow the official .NET naming guidelines
(https://learn.microsoft.com/zh-cn/dotnet/csharp/fundamentals/coding-style/identifier-names):

- **PascalCase** — types (class/struct/enum/interface), methods, properties, events, namespaces, enum members, `public`/`protected`/`internal` fields, and `public`/`protected`/`internal` constants (`const` / `static readonly`).
- **Interfaces** — `I` prefix + PascalCase (e.g. `ILiquid2DSolver`, `ILiquid2DForceReceiver`).
- **Private fields — always `_camelCase` with a leading underscore, regardless of `static` / `readonly` / `const`.** The underscore prefix is determined by *visibility* (private), not by lifetime: a `private static readonly Color _colorOk` and a `private const int _maxRetries` both take the underscore. (This also covers `Shader.PropertyToID` static caches.) Accessible constants — `public`/`protected`/`internal` `const` / `static readonly` — use PascalCase.
- **Method parameters & local variables** — `camelCase`.
- **Generic type parameters** — `T` prefix + PascalCase (`T`, `TValue`, `TKey`).
- ⚠️ **Serialization caveat:** changing a serialized field's name (including its first-letter case) **breaks already-saved YAML** — Unity binds by field name, so old data fails to load and reverts to defaults. When renaming such a field, migrate existing assets (scenes/prefabs/`.asset`/Volume profiles) or add `[FormerlySerializedAs("oldName")]`.
- ⚠️ **Shader/compute identifier exception:** string literals passed to `Shader.PropertyToID(...)` must match the names declared in the shader/compute file **exactly** (e.g. `_MainTex`, `_Color`, `_BlurOffset`; in `Liquid2DSph.compute`, buffers PascalCase like `Positions`, scalars camelCase like `dt`/`h`). These are shader names, not C# members — C# naming conventions do not apply.

### Unity Object null checks

For types deriving from `UnityEngine.Object` (MonoBehaviour, ScriptableObject, Material, GameObject, Sprite, …), prefer the implicit-bool form `if (obj)` / `if (!obj)` over `obj != null` / `obj == null`. Unity overloads the bool operator and `==`; the bool form is the cheaper, idiomatic path and also correctly treats a destroyed-but-not-yet-GC'd object as "null". (Plain C# objects still use `is null` / `!= null` as usual.)
